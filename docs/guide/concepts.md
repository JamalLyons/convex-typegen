# Concepts

## Path-scoped names

Generated function references follow Convex module paths. For example,
`convex/admin/users.ts` exporting `list` produces `api::admin::users::list`, whose `path()` is
`"admin/users:list"`. The corresponding `ListArgs` and `ListReturn` types live in that module.
Names use snake_case for Rust modules and fields, while Serde preserves the exact Convex wire keys.
No v0.4 aliases are emitted. See [generated models](../generated-models.md#function-references-and-model-names).

Tables are available from the generated `tables` module. `model::Id<tables::Tasks>` carries the
table at compile time; `model::Doc<tables::Tasks>` is the generated document type.

## Nullable string enums

For a `users` table with a role field declared as
`v.nullable(v.union(v.literal("admin"), v.literal("member")))`, the generated
field is `Option<UsersDocRole>`. Set it to `Some(UsersDocRole::Admin)` to send
`"admin"` or to `None` to send null. With an additional `v.optional(...)`, use
`None` to omit the role and `Some(None)` to send null.
See [generated models](../generated-models.md#presence-unions-and-literals).

## Generator and runtime crates

Use two crates with the same release version:

- `convex-typegen` is a build dependency. It parses the schema and function sources/spec and emits
  Rust bindings. It has no Convex client dependency.
- `convex-typegen-runtime` is a normal application dependency. It supplies generated-code support,
  the `ConvexValue` derive, `TypedClient`, model types, and direct Serde conversion for
  `convex::Value`.

The crates do not re-export each other. Import generator APIs from `convex_typegen` and runtime
APIs from `convex_typegen_runtime`. If application code imports `convex` directly, add `convex` as
its own dependency.

## Versions and Rust versions

Pair `convex-typegen` and `convex-typegen-runtime` at the same release. Regenerate bindings when
upgrading so the generated code and runtime agree. The runtime's MSRV is Rust **1.85**. Building
the generator in a consumer's `build.rs` requires Rust **1.97**. If you check in generated output
and do not run the generator as part of your Rust build, the runtime alone supports Rust 1.85.

From 1.0 onward, breaking library API changes and intentional breaking generated-name/type changes
require a major release. See the [semver policy](../semver-policy.md). In particular, generated
names are part of your application's compile-time contract even though generated output is not
itself the Rust library API.

## Build output and the function spec

The default `convex_typegen::build::generate_out_dir()` helper writes
`$OUT_DIR/convex_api.rs`; load it with `convex_typegen_runtime::include!()`. This keeps generated
files out of source control and lets Cargo rebuild when inputs change. Build scripts stay offline:
they only read TypeScript and JSON inputs.

Committed output is opt-in. Set `Configuration::out_file` to a checked-in path and call
`convex_typegen::generate`, or pass `--output PATH` to the CLI. The CLI `--check --output PATH`
checks generated bytes without writing and exits nonzero if output is absent or stale. The CLI
requires `--output` when it is not running with Cargo's `OUT_DIR`.

A committed `convex function-spec` file is an independent optional input selected with
`Configuration::function_spec_path` or CLI `--function-spec PATH`. It replaces TypeScript function
discovery, but schema parsing remains TypeScript-based. Refresh it explicitly against a deployed
local self-hosted backend. See [getting started](getting-started.md#capture-and-refresh-a-committed-function-spec).

## Choosing a macro

- `convex_typegen_runtime::include!()` includes the default generated file from `OUT_DIR` inside a
  Rust module. Pass a filename literal when the build script chose a custom filename.
- `#[derive(convex_typegen_runtime::ConvexValue)]` is for handwritten concrete Rust models that
  need the Convex wire representation. Generated models already use this derive. It implements
  Serde support; pair it with `value_serde::{to_value, from_value}` when converting SDK values.

Neither macro runs code generation or accesses the network. The generator remains a separate,
offline build dependency. See [macro details](../macros.md).
